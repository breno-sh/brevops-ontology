Para quem reimplementa

Esta página é o contrato do procedimento. O GRAIN-REPRO implementa a partir só dela (sem ler src/bo/grain/) e mede a concordância; desacordo vira emenda das regras ou UNKNOWN. São normativos: as seções Evidência, Normalização, Identidade, Regras, Resolução, Saída C19, Instância e a tabela aspecto → alegação (Adaptadores), e o arquivo grain/grain_rules.yaml (a parte executável das regras; seu sha256 está em grain/RULES.sha256). O resto (resultados, achados) é informativo. Nenhuma regra cita provedor, prefixo de tipo ou sufixo de nome: o que cada provedor diz entra pelos adaptadores de evidência, que são permitidos e ficam fora das regras.

Em uma frase: para cada candidato a unidade, junta-se a evidência da API (identidade, chave de importação, chave de nome, controlador de ciclo de vida, dono, alcance, ligação com a API); deriva-se a classe de identidade; tenta-se G0 → G1 → G2 → G3 → G4 nessa ordem; a primeira regra cujo match vale decide, e se lhe falta evidência o resultado é UNKNOWN com a lista do que falta, sem cair para a regra seguinte.

Três camadas

camadao que é
apioperação e recurso da API do serviço (onde nascem identidade, ciclo de vida, dono e alcance)
terraformrecurso, bloco aninhado ou grupo de atributos do schema do provider (só embalagem)
domainunidade canônica (ENTITY, COMPONENT, FACET, BINDING ou UNKNOWN), rótulo vindo da camada de API

Um candidato é um elemento da camada Terraform: um tipo de recurso (tipo), um bloco aninhado (tipo.bloco.subbloco) ou um grupo de atributos que a evidência liga a um aspecto da API (tipo.bloco:grupo). A unidade de domínio sai da camada de API (o rótulo vem dela); a camada Terraform é só embalagem e fica registrada em layers.terraform.

Evidência estruturada

Cada campo é uma lista de alegações (uma por fonte). Toda alegação pode trazer source (item de evidência do C00: nível publicado/derivado/interpretado e ref, doc ou citação) e status: unknown (a fonte não sabe) ou status: contradictory (a fonte diz que as fontes divergem).

Consolidação de um campo

  1. Alguma alegação com status: contradictory → CONTRADICTORY.
  2. Descartam-se as alegações unknown. Nenhuma sobrou → UNKNOWN.
  3. Normaliza-se cada alegação (listas ordenadas; via vira lista ordenada; booleanos ausentes = falso) e compara-se por JSON canônico. Todas iguais → KNOWN com esse valor; senão → CONTRADICTORY.

Ao lado das alegações, o adaptador entrega por candidato: field_map (nome canônico do campo → path relativo no candidato, normalizador norm, ref: true se é referência, config: true se é configuração, by_name: true se a referência é pelo nome de um elemento irmão); references (campo de referência → candidato-alvo); parent_role (papel do pai estrutural quando ele entra numa tupla de vínculo; padrão parent); groups (grupos de atributos ligados a aspectos, com a evidência própria de cada grupo). Os nomes nas chaves de identidade são os nomes canônicos do field_map, nunca o nome do provedor.

Normalização de cima para baixo

  1. T0: blocos e recursos marcados pela evidência como carga útil da API do pai (api_resource=payload, sem identidade própria) são transparentes; os átomos sobem para o pai e os blocos filhos passam a ter como pai estrutural o pai dele
  2. T1: grupos de atributos que a evidência liga a um aspecto da API viram candidatos próprios, como se fossem blocos
  3. T2: atributo cujo tipo cty é lista ou conjunto de objetos vira bloco repetido; os campos saem do próprio tipo como sub-átomos virtuais (caminho atributo.campo), marcados como derivados do tipo e não do schema de blocos; o átomo da coleção fica com o contêiner
  4. R: as regras abaixo são tentadas por prioridade crescente; a primeira cujo match vale decide; se faltar evidência listada em needs, o resultado é UNKNOWN com essa lista e as regras de prioridade menor NÃO são tentadas; se o guard é falso, tenta-se a próxima
  5. Z: se nenhuma regra decide, o resultado é UNKNOWN (GRAIN-G0-NOMATCH) com os campos cujos guards falharam

Coleção de objetos (T2, emenda GRAIN-A2): atributo cujo tf_type cty é ["list"|"set", ["object", {campo: tipo}]] (ou a forma nested_type [modo, {...}, opcionais]) vira o candidato tipo.bloco….atributo, com nesting = o modo e atributos = os campos do objeto, recursivamente para campos que também são coleções. Os sub-átomos provedor:tipo:caminho.atributo.campo são VIRTUAIS: derivados do tipo cty, não do schema de blocos (os átomos do SCHEMA-* não são regenerados); o átomo da coleção (…atributo) fica com a unidade do contêiner. O verificador de cobertura aceita sub-átomo virtual só sob um átomo de coleção do C01. Lista de objetos com um só elemento não muda nada: a cardinalidade não decide.

Transparente (T0) = api_resource KNOWN com status: payload E identity KNOWN com status: absent. O pai efetivo de um transparente aninhado é o pai estrutural (já pulando outros transparentes); o de um recurso de topo transparente é o alvo da única referência da sua chave de importação (sem ela, não é transparente). Átomos de um transparente vão para a unidade do pai efetivo, com path_in_unit = caminho a partir do bloco do pai (ou o caminho completo no próprio tipo, quando o pai é outro recurso).

Ordem: um nó depende do pai estrutural efetivo e dos alvos dos campos de referência citados nas alegações de identidade, chave de importação, ciclo de vida, dono e alcance. Decide-se em ordem topológica (empate: ordem lexicográfica do id, o que não muda nenhuma decisão porque cada uma só lê as dependências). Nó com dono em dois ou mais campos (owner.via com 2+ itens) espera também todo nó com duas ou mais referências na identidade (os vínculos possíveis), salvo se isso fechar ciclo. O que sobrar num ciclo sai UNKNOWN com identity (GRAIN-G0-CYCLE).

Classe de identidade

Notação: idf, imp, nk = identity, import_key, element_name_key consolidados; R = campos com ref: true no field_map.

  1. Algum dos três CONTRADICTORY → CONTRADICTORY. Os três UNKNOWN → ABSENT.
  2. api_resource KNOWN payload e idf não KNOWN → ABSENT.
  3. Se idf = present: escopo, surrogate, anonymous vêm dele; chave própria da API = key_fields fora de R (vazia se surrogate); referências da API = key_fields em R. Se imp = present: referências = fields em R; chave própria = fields fora de R. Se nk = present: chave própria = fields.
  4. As chaves próprias NÃO vazias das três fontes têm de ser o mesmo conjunto, senão CONTRADICTORY. idf = absent com chave própria em imp ou nk → CONTRADICTORY; nk present com anonymous → CONTRADICTORY.
  5. Relativa ao pai = idf absent, ou escopo within_parent, ou nk present sem escopo declarado. Relativa e aninhada → acrescenta-se a referência $parent (o pai estrutural efetivo). Relativa, de topo, sem nenhuma referência e não absent → CONTRADICTORY.
  6. Aninhado sem escopo, sem nk, sem referência e sem idf KNOWN → ABSENT.
  7. Surrogate com imp UNKNOWN e sem nk → ABSENT (o id opaco não diz o que o objeto liga). Surrogate sem chave própria e sem referência → chave própria = $id.
  8. Resolve-se cada referência da chave ($parent e os campos). Alvo ausente ou decidido UNKNOWN → UNRESOLVED.
  9. O = chave própria; T = alvos (na camada de schema, um por campo, porque dois papéis podem ter o mesmo tipo; na de instância, alvos distintos). Classes:
  • CONTRADICTORY: identidade, chave de importação ou chave de nome em CONTRADICTORY, ou chaves afirmadas que divergem
  • ABSENT: identidade, chave de importação e chave de nome todas UNKNOWN; ou só um id opaco (surrogate) sem a chave de importação afirmada (presente ou ausente), porque o id opaco não diz o que o objeto liga; ou bloco aninhado sem o escopo da identidade; ou candidato ligado à carga útil da API do pai sem alegação de identidade (sem ela não se sabe se é transparente ou elemento)
  • UNRESOLVED: alguma referência de K sem alvo resolvido, ou com alvo decidido UNKNOWN
  • ORPHAN: O e T vazios
  • BORROWED: O vazio e uma única unidade em T
  • REF_TUPLE: O vazio e duas ou mais unidades em T
  • INDEPENDENT: O não vazio e T vazio
  • WITHIN: O não vazio e uma única unidade em T
  • REF_TUPLE_PLUS: O não vazio e duas ou mais unidades em T

key_fields do C19 = chave própria (sem $id) mais os campos de referência da chave (sem $parent); se vazio e surrogate, os key_fields da alegação. anonymous = há chave própria, ela não é nome (sem nk e alegação anonymous) e não é $id.

Avaliação

  1. Para cada regra em prioridade crescente: se algum predicado de match é falso, passa-se à próxima.
  2. G0-IDENTITY casou → UNKNOWN; missing = identity + os campos de also_missing_if_unknown que não estão KNOWN + ciclo de vida, dono e alcance cujo via aponta para uma referência não resolvida.
  3. G0-NOMATCH (match vazio, sempre casa) → UNKNOWN; missing = os campos lidos pelos predicados de guard que falharam nas regras anteriores, na ordem do C19, ou identity se nenhum.
  4. Outra regra casou: se algum campo de needs não está KNOWN, ou está KNOWN mas o alvo do seu via não resolve, o resultado é UNKNOWN (GRAIN-G0-NEEDS) com esses campos. Não se tenta a próxima regra: falta de evidência nunca vira outro grão.
  5. Senão avalia-se guard: todos verdadeiros → o grão da regra; algum falso → anota-se o campo lido e passa-se à próxima regra.

Desfechos do procedimento

  • GRAIN-G0-NEEDS (UNKNOWN): o match de uma regra valeu, mas falta evidência listada em needs (ou o alvo dela não resolve); UNKNOWN com a lista; regras de prioridade menor não são tentadas
  • GRAIN-G0-CYCLE (UNKNOWN): o candidato depende (pai, alvo de referência ou dono) de si mesmo por um ciclo; UNKNOWN com identity
  • GRAIN-G0-DUPLICATE (UNKNOWN): na camada de instância, duas declarações distintas dão a mesma identidade de ocorrência com valores diferentes; as duas viram UNKNOWN com identity
  • GRAIN-T0-PAYLOAD (none): candidato transparente (carga útil da API do pai, sem identidade própria); não vira unidade, seus átomos ficam com o pai efetivo

Resolução de ciclo de vida, dono, alcance e pontas

  • via ausente: $parent se o nó é aninhado; senão, o único campo de referência da chave se T tem uma unidade; senão nada (não resolve).
  • Ciclo de vida e alcance com kind parent/container resolvem um único alvo; dono com kind parent resolve a lista de alvos de via. Kind self, provider, external, global não tem alvo. Alcance container sem via usa o via do dono.
  • Alvo que não resolve (ausente ou UNKNOWN) torna o campo "faltando" para needs e para G0.
  • Dono com 2+ alvos: procura-se, entre os vínculos já decididos, um cujas pontas (multiconjunto ordenado) sejam exatamente esses alvos; achou → o dono passa a ser esse vínculo (a faceta fica no vínculo). Não achou → o guard de G3 falha e o resultado é UNKNOWN com owner. A alternativa "declarar a lista de donos" não cabe no C19 3.0.0 (owner é um só objeto); ver Achados.
  • Pontas do vínculo (G1): papel → alvo, para cada referência da chave; $parent recebe o papel parent_role.
  • Pai emitido: G2 = alvo do ciclo de vida; G3 = alvo do dono (depois da troca por vínculo); G1, G4 = nenhum.

Camada de instância e identidade de ocorrência

Configuração: {"provider", "resources": [{"type", "name", "values"}]}; bloco single = objeto; list/set = lista; referência = {"$ref": "tipo.nome"}; valor não resolvido = {"$unknown": motivo}. Cada recurso, bloco presente e grupo com algum atributo presente vira um nó com a evidência do seu candidato; transparentes como na camada de schema (o de topo segue o $ref da sua única referência). Referência by_name: o valor é o nome de um elemento do candidato-alvo dentro do mesmo recurso (chave de nome com um campo); um único casamento resolve, senão não resolve. O mesmo motor decide cada nó, com as referências resolvidas entre ocorrências (alvos distintos).

Identidade de ocorrência = sha256 (hex) do JSON canônico (chaves ordenadas, separadores , e :, UTF-8 sem escape) de

{"grain": G, "label": rótulo, "parent": identidade do pai ou null, "endpoints": {papel: identidade da ponta} (só vínculo), "key": {campo da chave própria: valor normalizado, campo de referência da chave que não é o pai: identidade do alvo}}
  • ENTITY: parent null, key = chave própria. COMPONENT e FACET: parent = identidade do pai emitido. FACET: key vazia (o rótulo distingue os aspectos). BINDING: endpoints.
  • Valor ausente ou simbólico num campo da chave, chave só $id, ou pai/ponta/alvo sem identidade → ocorrência UNKNOWN com identity.
  • A posição textual nunca entra. Só entra como o campo $index (posição na lista), quando a evidência põe a ordem na chave (onde o provedor deriva o índice da ordem).
  • Normalizadores: str (sem espaços nas pontas), lower, int, bool (true/enabled/on/yes e false/disabled/off/no/suspended), cidr (rede canônica, sem bits de host), set_of_* (lista ordenada sem repetição do JSON canônico de cada item), ordinal (= int).
  • Duas declarações com a mesma identidade: com a mesma configuração normalizada, uma ocorrência só (as duas camadas Terraform anotadas); com configuração diferente, as duas UNKNOWN (GRAIN-G0-DUPLICATE).
  • Comparação entre embalagens: por ocorrência, (identidade, grão, rótulo, pai, pontas, chave, configuração normalizada pelos nomes canônicos config: true do próprio nó e dos transparentes que sobem para ele, referências simples fora da chave, regra, missing). A camada Terraform não entra.

Adaptadores de evidência

  • FixtureAdapter: a tabela {candidato: {campo: [alegações], field_map, references, parent_role, groups, roles}}, usada pelos mundos sintéticos.
  • C25Adapter (service_evidence.jsonl do SERVICE-EVIDENCE, C25 1.0.0). Se algum registro traz value.aspect (a forma real do SERVICE-EVIDENCE), todos os fatos de grão do provedor passam pela tabela por aspecto abaixo (emenda GRAIN-A1, CC-1). Fato afirmado sem aspecto segue a convenção anterior (T99).

Tabela aspecto → alegação (normativa)

  • Nada é inventado: aspecto sem tradução, aspecto fora da tabela e fato com status unknown viram alegação UNKNOWN com o motivo, que fica na fonte da alegação e nos motivos do relatório; a consolidação os ignora.
  • Dono da IDENTIDADE (identity_scope, parent, parent_attribute) não é dono da CONFIGURAÇÃO: nunca vira o campo owner. Por isso, hoje, nenhum aspecto dá owner a um tipo de topo: só os blocos (block_config_owner) e os fatos T99.
  • destroy_effect suspend num recurso separado é indício de faceta do pai; not_deleted e state_only dizem que o destroy não apaga, não quem apaga.
  • Bloco aninhado só ganha alegação com fato de block_path; sem ela é UNKNOWN pela G0, nunca FACET por omissão. Aspecto de bloco sem ligação com a API (não há block_api) deixa o bloco UNKNOWN com api_resource.
  • Nenhuma heurística de nome: block_schema.facet_word não é lido; alvo de referência só pela chave compartilhada (T02) ou por fato explícito.
  • Fonte de cada alegação traduzida: {level: derived, ref: evidence_id, note: "<regra>: <fato>/<aspecto>"}. Ordem: primeiro todos os aspectos que não dependem de outro candidato; depois T02 (que lê o ciclo de vida já consolidado dos pares), T21, T01/T10 com as referências e T40.

Achados e decisões (inclusive contra a hipótese)

  • A bateria de mutação achou um caso em que faltar a alegação de identidade de um recurso de carga útil o fazia virar faceta incompleta sem listar identity: a chave de importação dava identidade emprestada, mas só a alegação de identidade diz se o candidato é transparente. Correção: carga útil sem alegação de identidade é ABSENT.
  • Id opaco da API sem a chave de importação afirmada fazia uma anexação parecer entidade independente. Correção: surrogate sem import_key KNOWN é ABSENT. Sem isso, faltar evidência viraria ENTITY.
  • Na camada de schema, um vínculo entre dois objetos do mesmo tipo (rede ↔ rede) tem alvos iguais; contar alvos distintos o fazia parecer faceta. As pontas são contadas por papel no schema e por ocorrência na instância.
  • A prioridade G1 > G4 pedida pelo plano é garantida em boa parte pela classe de identidade (uma chave só de referências nunca é INDEPENDENT). A prioridade que de fato decide é G1 > G2: numa anexação embutida com ciclo de vida preso à instância, G1 e G2 aceitam a evidência, e trocar a ordem troca BINDING por COMPONENT (caso P4).
  • Elementos embutidos que se referem a irmãos pelo nome (regra → pool no balanceador embutido) precisam de referência by_name; sem ela, o grafo embutido perde relações que o separado tem.
  • Emenda 0.1.1 (CC-1): a primeira versão lia uma convenção que o SERVICE-EVIDENCE nunca gravou; os testes sintéticos usavam a mesma convenção e não pegaram. Entraram o adaptador por aspecto e testes com o arquivo real.
  • Emenda 0.1.7 (regra nova G2-CHILD, decisão do coordenador): um sub-recurso com CRUD próprio na API continua sendo parte do pai; ter API própria não o torna entidade independente. Justificativa: a identidade dele só existe dentro do pai (o caminho da spec o põe abaixo do pai, …/pai/{p}/filho/{f}), o pai o apaga em cascata, e as operações próprias só mudam QUEM pode criá-lo e apagá-lo sem mexer no resto do pai, não a quem ele pertence. A regra exige: classe WITHIN ou REF_TUPLE_PLUS em que as referências da chave que não são namespace apontam para UM pai marcado pela evidência como segmento de caminho acima (T54: o tipo de API da ponte está aninhado no tipo de API do pai de contenção; no bloco gêmeo, o pai estrutural herda a marca) e ciclo de vida de API publicado self. Sai COMPONENT do pai, com own_api_lifecycle=true e cascade_delete_by apontando o pai (itens de evidência no C19). Junto: G1 passa a contar as pontas sem os contêineres de namespace (senão a regra filha virava vínculo entre o pai e o grupo de recursos), e T52b leva a marca de namespace do pai ao filho. Controles negativos: a entidade sob namespace (G4-NS) continua ENTITY; faceta sem CRUD próprio continua FACET; filho sem ciclo de vida self segue a G2 comum; sem a marca de caminho, segue UNKNOWN.
  • Emenda 0.1.7, ainda (fatos de API da regra de SG da AWS, SE ce1e590): a identidade de API da regra (SecurityGroupRuleId) contradizia a identidade de recurso do Terraform (id), e uma referência tipada tirada da frase da doc punha o próprio identificador como referência a outro tipo. A identidade da camada de API agora prevalece (T56, T56b), e o pai sem via é resolvido pelo recurso pai da spec (T55). Resultado: regra embutida e regra separada saem COMPONENT do SG pela G2 comum (ciclo de vida do pai), e o E2 decide igual nos três pares.
  • Emenda 0.1.6, ainda: com o SERVICE-EVIDENCE do CC-10 (767bb22), pontes que nomeiam o mesmo recurso com grafia diferente (doc "objectstorage/Bucket" e spec "object_storage/bucket") contradiziam-se; T53 as unifica. Blocos que herdam do gêmeo (T09) podem sair FACET quando o gêmeo tem ligação de API de aspecto: é evidência herdada, não omissão.
  • Emenda 0.1.6 (regra nova G4-NS, decisão do coordenador): identidade qualificada por um contêiner de NAMESPACE (grupo de recursos, compartimento; conta, região e projeto já eram escopo do provedor) não é composição. Justificativa: o contêiner de namespace só dá unicidade ao nome; a configuração e o ciclo de vida de API da unidade são dela, e o apagamento em cascata pelo namespace é efeito do contêiner, registrado como relação cascade_delete_by (item de evidência cascade_delete_by=<unit_id> no C19 e relação nos verificadores), nunca como dono nem como ciclo de vida do pai. A regra exige: classe WITHIN ou REF_TUPLE_PLUS com TODAS as referências da chave marcadas namespace pela evidência (T52), ciclo de vida de API self, dono self e ligação de API de recurso. Sem a marca, a contenção segue composição e o resultado segue UNKNOWN; uma faceta verdadeira (ciclo de vida do pai) nunca passa, porque o guard pede self (controle negativo nos testes).
  • Emenda 0.1.5 (T51, pai fora da fatia): o grupo de recursos do Azure deixou de impedir a identidade (contêiner externo). Achado: o NSG e a conta de armazenamento passam de UNRESOLVED a G0-NOMATCH com lifecycle_controller, porque a identidade é relativa ao grupo de recursos e o ciclo de vida de API publicado é self; G2 pede ciclo de vida preso ao pai e G4 pede identidade independente. A evidência não exprime "apagado pela própria operação E em cascata pelo grupo"; fica UNKNOWN até a evidência ou uma emenda de regra (depois do GRAIN-REPRO) decidir.
  • Emenda 0.1.4 (CC-8): com os fatos da spec (R-BRIDGE-SPEC, R-LIFE-SPEC, R-LIFE-SPEC-PARENT, R-OWN-SPEC, camada de API) o contêiner da AWS decide (ENTITY) e o bloqueio de acesso público separado decide FACET dele. Três defeitos do adaptador apareceram só com esse dado: a ponte (status resource) contradizia o suspend (status aspect) — T49; o suspend sem via contradizia a spec com via bucket — T50; e a chave compartilhada tinha duas raízes com ciclo de vida próprio — o desempate pelo parent_resource da spec (T02). As 12 disputas spec × doc saem CONTRADICTORY, de propósito. As demais facetas separadas da AWS ficam UNKNOWN só por effective_scope (o alcance de API ainda não é publicado para elas).
  • Emenda 0.1.3 (CC-1d, CC-1e): a herança do gêmeo testava via in conjunto antes de ver se via era lista (TypeError no azurerm). Fatos de API sem aspecto (R-OWN-API, R-LIFE-API, R-SCOPE-SELF com layer api) são consumidos; com layer terraform continuam recusados. Achado no caminho: com a referência tipada ao contêiner fora da chave, um escopo de criptografia filho da conta saía ENTITY; a contenção (owner/parent) agora põe essa referência na chave, e o caso volta a UNKNOWN (contêiner sem decisão), que é o que a evidência sustenta.
  • Emenda 0.1.2 (CC-1b, CC-1c): o adaptador 0.1.1 era anterior aos fatos de gêmeo, referência tipada e timeouts do SERVICE-EVIDENCE; os blocos embutidos saíam com "twin_type sem tradução" e o E2 não chegava ao grão. Achado no caminho: os fatos block_* do bloco (camada Terraform) contradiziam a identidade herdada do gêmeo; a evidência do gêmeo agora substitui a do bloco. Fatos sem aspecto com layer terraform (R-OWN-TOP, R-LIFE-TF) não viram dono de tipo de topo nem ciclo de vida: aceitá-los faria toda faceta separada dona de si.
  • Emenda 0.1.1 (CC-NET-1): regras embutidas como atributo lista/conjunto de objetos não viravam unidade; agora viram bloco repetido (T2) com sub-átomos virtuais, e embutido × separado dá a mesma decomposição com a mesma evidência de API.
  • A emenda 3.1.0 do C19 (CONTRACTS) trouxe endpoints e owner.refs, propostos aqui: as pontas do vínculo saem em endpoints (antes iam em identity.evidence). Faceta de vários donos SEM vínculo entre eles continua UNKNOWN com owner nas regras 0.1.1; usar owner.refs para ela é decisão de regra (G3 tem um só pai) e fica para emenda depois do GRAIN-REPRO. O C25 1.0.0 não tem fact_kind para chave de nome nem para alvo de referência; a convenção de value acima os carrega.

Limites

  • Tudo aqui roda em mundos sintéticos (provedores provider_a a provider_h); os 4 schemas reais entram no DECOMPOSE, e o GRAIN-REPRO roda os gabaritos adversariais reais.
  • A qualidade da decomposição é a da evidência: o procedimento não inventa identidade, dono, alcance nem ciclo de vida; onde a evidência falta, o resultado é UNKNOWN, e o número de UNKNOWN é resultado, não defeito a esvaziar.
  • Dado real (SERVICE-EVIDENCE da onda atual, medido por python -I -m bo.grain.realdata e pelos testes test_grain_real_*): a fatia de armazenamento não levanta mais EvidenceError, mas os contêineres dos quatro provedores saem UNKNOWN, porque faltam fatos, não tradução: nenhum aspecto dá dono da configuração a tipo de topo; o ciclo de vida do contêiner é not_documented (AWS, Azure, OCI) ou só tem deletion_policy sem valores (Google); a ponte de API é UNKNOWN na AWS e no Google; a chave compartilhada da AWS não tem raiz com ciclo de vida self; a contenção do Azure não diz o atributo de referência. Com o gêmeo (T09) e a referência tipada (T44), o E2 no dado real sai igual para SG ingress, SG egress e NSG security_rule (mesmo grão, regra, falta, rótulo e relações; os dois lados ainda UNKNOWN pela mesma falta). Os controles positivos dos testes mostram que, com esses fatos, o mesmo caminho decide o contêiner (ENTITY), a faceta separada (FACET) e a regra embutida igual à separada (COMPONENT, mesmas relações).
  • O lint é lexical e de higiene; validade vem dos compromissos, do GRAIN-REPRO e dos pilotos.
  • Regras provisórias: mudam só por emenda versionada depois do GRAIN-REPRO e do PILOT-EXIT.
